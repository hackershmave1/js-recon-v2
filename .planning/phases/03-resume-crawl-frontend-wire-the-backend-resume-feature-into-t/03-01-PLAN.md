<objective>
Wire the backend resume feature into the dashboard UI by adding a single "Continue Crawl" button to each eligible session row in dashboard.js.

Purpose: Users currently cannot resume a stopped/failed crawl without manually re-creating a session and pasting the URL. The backend already accepts `resume: true` on POST /api/recon/jobs/start (recon.py:55) and handles all skip-logic server-side. This plan is pure frontend glue.

Output: A modified `api/app/static/dashboard.js` containing (1) a new `continueCrawl(sessionId)` async method, (2) a conditionally-rendered button in the session row action bar, and (3) an extension to `patchSessionReconProgressRow` that keeps the new button's state in sync during polling.
</objective>

```javascript
async continueCrawl(sessionId) {
    if (!sessionId) return;
    const reconState = this.reconSessionProgress.get(sessionId) || null;
    if (!reconState) return;
    const reconStatus = String(reconState.status || '').toLowerCase();
    if (['queued', 'running', 'cancelling'].includes(reconStatus)) return;

    const url = reconState.targets?.[0];
    if (!url) {
        this.showAlert('Cannot resume: no target URL recorded for this session.', 'warning');
        return;
    }

    const btn = document.querySelector(`[data-session-continue-id="${sessionId}"]`);
    if (btn) {
        btn.disabled = true;
        btn.innerHTML = '<i class="fas fa-spinner fa-spin me-1"></i>Starting...';
    }

    try {
        const payload = {
            sessionId,
            url,
            resume: true,
            discoveryEngine:   reconState.options?.discoveryEngine   || 'katana',
            sameOriginOnly:    reconState.options?.sameOriginOnly    ?? true,
            includeSourceMaps: reconState.options?.includeSourceMaps ?? true,
            performAnalysis:   reconState.options?.performAnalysis   ?? true,
            maxAssets:         reconState.options?.maxAssets         || 500,
            maxDepth:          reconState.options?.maxDepth          ?? 3,
            timeoutSeconds:    reconState.options?.timeoutSeconds    || 20,
            waitAfterLoadMs:   reconState.options?.waitAfterLoadMs   ?? 2500,
            maxResponseBytes:  reconState.options?.maxResponseBytes  || (12 * 1024 * 1024),
        };

        const response = await axios.post(`${this.apiBase}/api/recon/jobs/start`, payload);
        const data = response.data || {};
        const jobId = data.jobId;
        const job = data.job || null;
        if (job && sessionId) {
            this.reconSessionProgress.set(sessionId, job);
        }
        if (jobId) {
            this.startReconJobPolling(jobId, sessionId);
        }
        this.showAlert(`Crawl resumed for session ${this.shortId(sessionId)}.`, 'success');
    } catch (error) {
        const detail = error?.response?.data?.detail;
        const message = typeof detail === 'string' ? detail : (detail?.message || error.message);
        this.showAlert(`Failed to resume crawl: ${message}`, 'danger');
    } finally {
        if (this.activeTab === 'sessions') {
            await this.loadSessions();
        }
    }
}
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser DOM -> continueCrawl method | User-controlled click; sessionId is rendered from DB-backed session.id |
| continueCrawl -> POST /api/recon/jobs/start | Crosses to the backend; url and options come from a DB-backed reconSessionProgress entry (not from user input) |
| Backend API -> continueCrawl response handling | Backend response is trusted; response.data.jobId / response.data.job are consumed as-is |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Tampering | `url` field sent in resume POST | accept | The url value originates from `reconState.targets[0]` which was stored in the DB by a prior recon job. It was validated on insert via `SecurityValidator.validate_url` (see recon.py start_recon_job handler). The backend re-validates on every `/api/recon/jobs/start` call, including resume. No new frontend validation required. |
| T-03-02 | Spoofing | sessionId embedded in data-session-continue-id attribute | accept | sessionId is rendered directly from `session.id` returned by the authenticated /api/sessions endpoint. It is already used in the existing data-session-analyze-id / data-session-delete-id attributes without issue. Same trust assumptions apply. |
| T-03-03 | Tampering | sessionId injection via template-literal interpolation in the onclick handler | mitigate | `session.id` is a DB-generated UUID (see models/session.py); it is NOT user input and cannot contain template-breaking characters. However, to stay consistent with existing patterns, the onclick uses `'${session.id}'` with single-quote delimiters exactly as `onclick="dashboard.analyzeSession('${session.id}')"` at line 2834 does. No additional escapeHtml needed because UUID charset is [0-9a-f-]. |
| T-03-04 | Information Disclosure | Error message shown in danger alert (`detail?.message || error.message`) | accept | The backend returns HTTPException detail strings that are already designed for user display (e.g., "Session not found", "Crawl is already running"). No sensitive internals leaked. This matches the error-handling pattern used in `submitCreateSessionFromModal` (dashboard.js:868-870). |
| T-03-05 | Denial of Service | User double-clicks Continue Crawl, firing two concurrent POSTs | mitigate | Task 1 disables the button BEFORE awaiting axios.post (inline DOM patch via querySelector). Task 3 also disables+hides the button on the next poll tick when the job becomes active. Additionally, the guard `if (['queued','running','cancelling'].includes(reconStatus)) return;` at the top of continueCrawl short-circuits a second call if reconSessionProgress was already updated. Backend also rejects concurrent jobs for the same session. |
| T-03-06 | Elevation of Privilege | continueCrawl bypasses session ownership checks | accept | The POST to /api/recon/jobs/start hits the same authenticated endpoint used by submitCreateSessionFromModal. Any session-ownership / auth checks enforced there apply identically to the resume flow. No new privilege surface is introduced. |
| T-03-07 | Repudiation | Resume action is untracked in logs | accept | The backend logs every `/api/recon/jobs/start` call including the resume flag. No additional frontend logging is required; this is a low-value event. |
